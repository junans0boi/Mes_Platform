# BE-08: ProcessUnitStatusCurrent 조회 API, ProjectionVersion, SignalR 이벤트

상태: 선행 완료 시 착수 가능  /  선행: CON-01, DB-02, BE-04, BE-03, BE-12  /  Gate: integration

## 목적

Projection 조회 API, Projection 갱신 흐름(Queue Claim → 계산 → Upsert → ProjectionVersion 기록 → Outbox 기록), Server의 Outbox Dispatcher와 SignalR 발행을 제공한다. 첫 수직 슬라이스에서는 **계산기 seam까지**를 구현하며 실제 `ProcessResult` 기반 도메인 계산은 구현하지 않는다. Worker→Server 전달은 BE-12 결정(Transactional Outbox)을 따른다.

## 범위

- CON-01의 `GET /api/v1/monitoring/process-unit-status`(cursor)와 `?ids=`(상한 100) 구현, 행에 `plantId`·`projectionVersion`
- **seam과 역할 구분**: `IProcessUnitStatusCalculator`(Application)는 Queue 항목(`PlantId`, `ProductionLotId`, `HousingQr` 또는 LOT 단위)에서 Projection 행 값을 **계산**한다. `IProjectionOutboxWriter`(Worker 쪽)는 Upsert transaction 안에서 Outbox 행을 **기록**한다. `IProjectionChangeNotifier`(Server 쪽)는 Dispatcher가 claim한 행을 SignalR Hub로 **발행**하는 인터페이스다. 세 역할은 서로 대체하지 않는다
- `ProjectionRefreshWorker`(BE-04 Worker host 위): Queue Claim → `IProcessUnitStatusCalculator` → Upsert + `ProjectionVersion` 기록 + `IProjectionOutboxWriter`로 Outbox Insert(**같은 transaction**) → Queue 완료. 테스트용 단일 반복 진입점 `RunOnceAsync`. Worker는 Hub를 직접 호출하지 않는다
- `ProjectionOutboxDispatcher`(Server hosted service): Outbox claim(lease) → `IProjectionChangeNotifier`로 발행 → `PublishedAt` 기록, 실패 시 attempt 증가·backoff, lease 만료 행 재claim, BE-12가 정한 정책과 설정값 사용. 테스트용 단일 반복 진입점 `RunOnceAsync`
- `IProjectionChangeNotifier`의 SignalR 구현과 Hub: Plant 구독(`allowedPlantIds` 검증), `ProjectionChangedEvent{projection,plantId,changedIds,reset?,asOf}` 발행, version 미포함(`contracts/realtime-events.md`)
- 변경 행 상한 초과 또는 범위 불명 시 `IsReset=1` Outbox 행과 `reset:true` 이벤트(빈 `changedIds`)
- **검증용 계산기**: 테스트·fixture 프로젝트에만 있는 deterministic calculator. 운영 host의 DI에는 등록하지 않음
- 운영 host에 계산기가 등록되지 않았으면 Projection Worker는 명확한 오류로 시작을 거부한다
- at-least-once: 중복 발행을 허용하고 클라이언트가 `projectionVersion`으로 안전하게 병합한다는 점을 코드 주석이 아닌 계약(`contracts/realtime-events.md`)과 이 티켓에 명시
- 통합 테스트 절차 기록(아래 Test method)

## 제외 범위

- **실제 `ProcessResult`·`ProductionLot` 기반 도메인 계산**: 원본 테이블과 계산 규칙이 아직 없으므로 후속 티켓으로 분리한다. 이 Epic에는 해당 티켓이 없다
- TVF 재계산과 정합성 검증
- DDL 작성(DB-02)
- SignalR backplane(다중 Server 간 Hub 전달, 후속)
- 1-2 이외 화면 전용 Query
- p95 측정과 대표 데이터 seed(BE-09)
- 이벤트 순서 보장

## 완료 조건

- [ ] 응답이 CON-01 계약과 일치하고 모든 행에 `plantId`, `projectionVersion`이 있다
- [ ] deterministic test calculator로 Queue Claim → 계산 → Upsert → `ProjectionVersion` 기록 → Outbox 기록(Worker) → Dispatcher claim → 발행(Server) 흐름이 통합 테스트로 끝까지 통과한다
- [ ] Worker는 Hub·notifier를 참조하지 않고 Outbox writer만 사용한다(아키텍처 테스트 또는 참조 검사)
- [ ] Upsert, `ProjectionVersion` 기록, Outbox Insert가 하나의 transaction이다: 계산 또는 Outbox 기록 실패 시 Projection 행·version·Outbox 행이 함께 rollback되고 Queue 항목은 재시도 가능 상태가 된다
- [ ] 같은 행의 version이 갱신마다 단조 증가한다
- [ ] 발행된 이벤트가 `ProjectionChangedEvent`와 필드까지 동일하고 version이 없으며 `plantId`가 행의 `PlantId`와 같다
- [ ] `IsReset=1`일 때 `reset=true`이고 `changedIds`가 빈 배열이다
- [ ] Dispatcher를 실행하지 않은 동안 Outbox 행이 `Pending`으로 남고, 이후 `RunOnceAsync`로 발행된다(Server 중단 시 유실 없음)
- [ ] 발행 후 `PublishedAt` 기록 전에 중단된 상황(발행은 됐으나 완료 미기록)이 재실행 시 같은 이벤트를 다시 발행하며, 이를 중복 이벤트로 받은 클라이언트 병합 규칙(FE-09)이 계약에 명시되어 있다
- [ ] lease가 만료된 행을 다른 Dispatcher가 재claim하고, lease가 유효한 행은 다른 Dispatcher가 발행하지 않는다
- [ ] 발행 실패 시 `AttemptCount`와 `NextAttemptAt`이 BE-12 정책대로 갱신되고 최대 시도 초과 시 `Failed`와 `LastError`가 남는다
- [ ] 허용되지 않은 Plant 구독이 거부된다
- [ ] 목록·`ids` Query가 DB-02의 Plant 선행 index를 사용한다(실행 계획 검증)
- [ ] 운영 host에 계산기가 없으면 Projection Worker가 시작을 거부한다
- [ ] 실제 ProcessResult 기반 계산이 구현되었다고 문서·완료 기록에 쓰지 않는다

## 테스트 방법

통합 테스트 절차(Infrastructure·API·Hub):

1. 별도 이름의 테스트 DB에 DB-01, DB-02 스크립트를 적용한다(운영 DB 차단 검사 포함).
2. fixture가 `dbo.Plant` 행을 만들고, `dbo.ProcessStatusRefreshQueue`에 Queue 행을 SQL로 직접 삽입한다(`Status`=대기). 원본 Command는 사용하지 않는다.
3. Worker 쪽 테스트 host에 deterministic test calculator를 등록하고 `ProjectionRefreshWorker.RunOnceAsync`를 직접 호출한다(백그라운드 스케줄에 의존하지 않음).
4. 검증(Worker): `ProcessUnitStatusCurrent` 행·`ProjectionVersion`, Queue 완료 상태, `ProjectionChangeOutbox`에 `Pending` 행이 같은 transaction으로 생겼는지 확인한다. 같은 Queue를 다시 넣어 version이 증가함을 확인한다.
5. rollback 검증: calculator 또는 Outbox writer가 예외를 던지게 하여 Projection 행·version·Outbox 행이 모두 남지 않고 Queue가 재시도 상태인지 확인한다.
6. Server 쪽 테스트 host에 기록용 `IProjectionChangeNotifier` fake를 등록하고 `ProjectionOutboxDispatcher.RunOnceAsync`를 직접 호출한다. fake가 받은 이벤트(`plantId`, `changedIds`/`reset`)와 Outbox `PublishedAt`을 확인한다. Dispatcher를 호출하기 전에는 `Pending`으로 남아 있음을 확인한다.
7. 중복·lease·retry 검증: 발행 후 `PublishedAt` 기록 전에 중단을 시뮬레이션해 재실행 시 중복 발행되는지, lease 만료 행의 재claim, 유효 lease 행의 비재claim, 실패 시 attempt·backoff·`Failed` 전이를 확인한다.
8. API·Hub 테스트: 적재된 행을 `GET …/process-unit-status`와 `?ids=`로 조회하고, SignalR notifier 구현이 구독 클라이언트에게 이벤트를 전달함을 확인한다.
9. 실행 계획 검증으로 Plant 선행 index 사용을 확인한다.
