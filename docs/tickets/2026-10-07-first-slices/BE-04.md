## 진행 기록 (2026-10-07)

**구현**
- Task 7: `X-Request-Id`·`X-Operation-Id`를 응답 시작 시점에 쓰는 `ResponseOperationHeadersMiddleware`(예외 핸들러가 헤더를 지우는 500, 401·403 포함). 로그 속성 `TraceId, RequestId, OperationId, ActorUserId, PlantId, Endpoint, UseCase`를 `OperationLogScope`(Infrastructure)와 `OperationLogScopeMiddleware`(인증 뒤)로 붙이고 요청 요약 로그에도 같은 속성을 넣는다. `LogRedactor`가 Bearer·JWT·암호·연결 문자열을 가린다. `AuditEntry` 검증은 이미 있었다(DB writer는 계획대로 제외).
- Task 8: Worker 호스트. 기본값은 모두 비활성이며 `Worker:Enabled`와 `Worker:ProcessRole=Worker`가 모두 있어야 한다. `DatabaseSafetyGuard`가 `WORKER_DISABLED`, `WORKER_ROLE_INVALID`, `DATABASE_BLOCKED`, `WORKER_ALLOWED`(추가: `DATABASE_NAME_MISSING`)를 반환한다. 차단 목록 외에 이름에 `prod`가 들어간 DB도 거부한다(`database/apply.sh`와 같은 규칙). 거부되면 호스트·Job을 만들지 않고 DB에 연결하지 않는다. 등록된 Job은 `WorkerHeartbeatService` 하나다.
- Task 9: 아키텍처 테스트에 범용(제네릭) Controller, 이름으로 대상을 고르는 route, Controller의 SQL 접근을 잡는 규칙 추가(규칙 자체를 나쁜 예제로 검증하고, 실제로 나쁜 Controller를 넣어 실패하는 것을 확인했다). 기존 프로젝트 참조 행렬 테스트는 그대로 유지한다. `scripts/verify.ps1`, `.github/workflows/build.yml`, README 갱신.
- 기존 코드의 `dotnet format` 위반(SqlErrorMapper 정렬, using 순서)을 같은 도구로 정리했다. 의미 변경 없음.

**로컬 검증**
- `pwsh scripts/verify.ps1`: restore, format 검증, Release build(경고를 오류로 취급) 통과. 테스트는 Architecture 29/30, Application 45, Domain 12, Infrastructure 20, Api 57, Worker 22 통과. 실패 1건은 `Sdk_version_is_pinned`이며, 이 작업 환경에 SDK 10.0.112만 있어 `global.json`을 로컬에서만 임시로 `10.0.100`으로 바꿨기 때문이다(저장소 값은 10.0.400 그대로, 커밋 제외).
- Worker 실행: 기본 설정 → `WORKER_DISABLED` exit 0, prod 이름 DB → `DATABASE_BLOCKED` exit 2, 잘못된 role → `WORKER_ROLE_INVALID` exit 2, 허용 설정 → heartbeat 로그 출력 후 종료 신호로 정상 종료.

**남은 조건**: "CI가 build와 test를 수행한다"의 증거(CI 실행 링크). push가 허용되면 workflow가 실행되고 그 링크로 이 티켓을 닫는다.
